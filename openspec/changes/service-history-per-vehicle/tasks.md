- [ ] 2.10 Follow-up, HIGH severity, PRE-EXISTING (raised by GGA round 3 on PR #58, reproduced locally in `America/Panama`): **`appointmentAt` drifts by the UTC offset on every edit save, and it compounds.** `toDatetimeLocal` builds the input value from `date.toISOString().slice(0, 16)` — a UTC wall clock — and `handleSubmit` reads it back with `new Date(appointmentAt)`, which per ECMAScript parses an offset-less date-TIME string as LOCAL time (date-only strings parse as UTC; that asymmetry is the trap). Verified: stored `14:00Z` → input shows `14:00` → save → `19:00Z` → reopen → save → `00:00Z next day`. Worse than a wrong timestamp: `updateOrder` compares `getTime()`, so every one of those saves reads as a CHANGED appointment and cancels the customer's pending reminder to reschedule it at the drifted time. The `Number.isNaN` guard added in round 2 does not catch it — a drifted date is perfectly valid. NOT fixed here, deliberately: it predates WU2 and fixing it is scope expansion. But WU2 is what makes it matter, because the three note fields are `isEdit &&`-gated, so a technician now opens the edit dialog after every job where nobody routinely did before — a latent bug just became the normal path. Fix shape: build the input value from local getters (`getFullYear`/`getMonth`/…), and only send `appointmentAt` when it actually changed.
